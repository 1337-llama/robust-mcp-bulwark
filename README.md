# MCP Bulwark

> A security gateway for AI agents. MCP Bulwark sits between an agent and its MCP tools. It pins and inspects tool definitions, enforces least-privilege policy on every tool call, redacts secrets, and keeps a tamper-evident audit trail. Every protection is proven by an attack test that runs in CI.

**Status: 🚧 Design phase. No code yet.** This project follows a spec-driven process ([docs/WORKFLOW.md](docs/WORKFLOW.md)): idea → design → specs → build. The design documents are part of the project.

## The problem

AI agents get real capabilities (files, shells, email, cloud APIs) through the **Model Context Protocol (MCP)**. That opens new attack paths:

```
 Agent ──► [ poisoned tool description ]   ──► model follows hidden instructions
 Agent ──► [ tool changes after approval ] ──► "rug pull": trusted tool turns malicious
 Agent ──► [ web page with injection ]     ──► agent reads private data ──► sends it out
```

Published research shows popular models often fall for tool poisoning: several exceeded 60% attack success in the MCPTox benchmark (2025). Most current defenses are install-time scanners or chat-content filters, and few publish evidence that their protections work.

## What MCP Bulwark does

| Capability | How |
|---|---|
| **Pin and diff** | Records a fingerprint of every approved tool definition. Any change quarantines the tool and shows a readable diff. |
| **Inspect** | Analyzers flag hidden instructions, invisible Unicode, cross-tool manipulation, and suspicious schemas. |
| **Decide** | Policy-as-code allows or denies each call: which tool, with which arguments (paths, domains, patterns). |
| **Redact** | Detects secrets in tool arguments and results before they leak. |
| **Record** | Hash-chained, SIEM-friendly audit log of every decision and its reasons. |
| **Contain** *(v0.2)* | Once a session has touched both private data and untrusted content, tools that can send data out are locked down. |

It's a drop-in wrapper: `bulwark wrap -- <server command>`.

## Proven by attacks, not claims

The repo includes an **attack suite**: deliberately malicious (harmless) MCP servers plus a scripted client that replays exactly what a hijacked agent would send. On every change, CI runs each attack twice: once directly, where the attack must succeed, and once through Bulwark, where it must be blocked or detected.

## Roadmap: attacks first, then defenses

| Milestone | Deliverable |
|---|---|
| **M1** | Attack suite + transparent stdio proxy + audit log |
| M2 | Tool pinning, static analyzers, CLI, detection-rate tests |
| M3 | Policy engine, argument constraints, secret redaction, one-command demo, signed release. **v0.1** |
| M4 | Remote (HTTP) servers, multi-server support, taint tracking, human approval. **v0.2** |
| M5 | ML injection classifier, OpenTelemetry/OCSF export, optional live-model mode. **v0.3** |

Why this approach? See [ADR-0001](docs/adr/0001-lab-first-roadmap.md) and [ADR-0002](docs/adr/0002-gateway-with-attack-suite.md).

## Safety

The attack lab (`lab/`) contains **intentionally malicious MCP servers for testing only**. They use fake canary secrets, "exfiltrate" only to a local loopback sink, and make no external network calls. Don't connect them to agents that have access to real data.
